# Second-pass readability and compilation audit

## Scope

- Audited **all 58 checked-in Java source files**, including robot setup, intake, indexer, shooter, swerve drive, vision, climber, superstructure, constants, math utilities, simulation, and generated CTRE settings.
- Added **57 file-specific `STUDENT MAP` explanations** to the hand-edited Java files. The remaining file, `generated/TunerConstants.java`, is vendor-generated and was kept as supplied.
- Added **107 `STUDENT NOTE` explanations** along important constructor, command, motor-output, and sensor paths; these complement the file-level guides and existing comments.
- Removed a misleading intake claim that renamed fields were unchanged. Fixed idle-mode and hub-status comments that described behavior not implemented by the code.
- Replaced private one-letter shooter calibration helper methods with descriptive names. Made CTRE shooter feedback/request field names more explicit. Kept numeric calibration, operator-button logic, and literal logging strings unchanged.
- Added `NINTH_GRADE_START_HERE.md` to explain the robot's physical subsystems, a button-to-motor code trace, basic Java syntax, and where advanced code should be deferred.

## Compilation and code preservation

**PASS — Independent Java 17 compile** of 69 verification units: 58 Java source files, the original BuildConstants, and temporary verification-only equivalents for classes normally generated by AdvantageKit and Lombok. Dependencies came from the bundled compiled application JAR in the original uploaded robot archive. All 69 units compiled successfully with `javac --release 17 -proc:none`.

**PASS — Literal audit:** all numeric, character, and string literal tokens in the 58 checked-in Java files match the immediately preceding English-naming ZIP. This includes CAN IDs, arm angles, motor gains, output strengths, and quoted PathPlanner command names.

**PASS — Change-scope audit:** executable-code differences versus the preceding ZIP are limited to the private shooter calibration helper/parameter names and private shooter motor-control request / feedback variable names. Other changes are documentation, whitespace, and removal of dead *commented-out* sample calibration lines. Robot program control flow and vendor method calls were not intentionally changed.

**PASS — Project resources:** non-Java, non-documentation files match the prior review ZIP byte-for-byte, including autonomous/PathPlanner data and vendordeps.

**NOT VERIFIED — Native Gradle/WPILib build:** The Gradle wrapper distribution needed to run the actual WPILib Gradle build is unavailable offline here. The compile pass uses test-only substitutes for generated methods/classes, not the normal Gradle annotation processors. The previous session likewise could not run a native Gradle build.

**NOT VERIFIED — Hardware or full physics behavior:** no real TalonFX, roboRIO, CAN bus, CANcoder, cameras, robot, Driver Station, or complete simulator test was run. This package must not be treated as deployment-verified.

## What this audit does not claim

The code is **approachable in a guided reading order** for a capable beginner. It is not true that every part can be understood by a ninth grader with no programming or robotics instruction: vendor APIs, asynchronous sensor queues, 3D geometry, PID, motion profiling, and projectile math still require lessons. Those areas are labeled so a student can skip them initially without misunderstanding the rest of the program.

## Check in WPILib VS Code before deployment

1. Extract the ZIP and open the folder containing `build.gradle`.
2. Select **WPILib: Build Robot Code**. Record whether it reports `BUILD SUCCESSFUL` and whether there are compiler errors.
3. If VS Code shows stale generated-class errors despite a successful build, refresh Java's language server workspace; do not remove valid program code to silence an editor warning.
4. Check the specific issues documented in `REVIEW_BEFORE_DEPLOYMENT.md` with experienced student programmers/mentors.
5. Test autonomous, teleop, disabled transitions, all intake arm and roller modes, swerve drive, indexer, flywheel/hood, camera localization, and logging on suitable test hardware before deploying to competition robot.
